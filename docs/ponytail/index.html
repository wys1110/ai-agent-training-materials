Ponytail Skill

최적화 요청했더니 엉뚱한 곳을 바꿨나요?

우선순위도 없고, 왜 바꿨는지 이유도 없고, 동작이 바뀐 것 같기도 하다면 Ponytail이 필요한 순간이다.

이 자료에서 다루는 것

왜 이 스킬이 필요한가 — 일반 최적화 요청의 문제점 켜면 뭐가 달라지는가 — 우선순위·안전성·명확성 언제 쓰면 좋은가 — 구체적인 상황 안전한가 — 잘못된 최적화를 어떻게 막는가

문제 · "최적화해줘" 한 마디의 위험

어디를 왜 바꿨는지 모르는 코드

"optimize this"라고 했더니 변수명을 바꾸고, 주석을 지우고, 알 수 없는 리팩터링을 해줬다. 빠르게 됐는지도 모르겠고, 동작이 같은지도 불확실하다.

흔한 문제들:

— 왜 이 함수를 바꿨나요?
"전반적으로 더 깔끔해 보여서요"

— 이 부분이 실제로 느렸나요?
"아마도요, 루프가 있으니까요"

— 동작이 달라진 건 없나요?
"같을 거예요"

→ 이 대답들이 불안하다면 Ponytail이 필요하다

문제 · 일반 최적화 요청의 4가지 문제

왜 그냥 "최적화해줘"는 위험한가

1 우선순위 없음 O(n²) 루프보다 변수명 정리를 먼저 한다. 임팩트와 무관한 순서.
2 동작 변경 위험 더 빠른 대신 에러 처리가 빠진다. 속도는 올라가고 안전성은 내려간다.
3 근거 없는 추측 프로파일링 없이 "여기가 느릴 것 같아서" 바꾼다. 실제 병목이 다른 곳일 수 있다.
4 범위 초과 최적화 요청인데 API 시그니처, 변수명, 코드 구조까지 바꾼다.

효과 · Ponytail이 바꾸는 것

가장 큰 병목부터. 동작은 절대 안 바꿈.

우선순위가 정해진 대상 목록을 순서대로 처리한다. 각 변경마다 이유를 명시하고, 동작·API·에러 처리는 손대지 않는다.

우선순위 순서 (항상 이 순서) O(n²) 루프 → N+1 쿼리 → 불필요한 할당 → 중복 연산 → 사용 안 하는 코드
매 변경마다 이렇게 알려준다 위치 → 문제 → 수정 → 이유. "n번 왕복 → 1번 JOIN"처럼 구체적으로.
절대 바꾸지 않는 것 동작, 공개 API 시그니처, 에러 처리 — 관찰 가능한 동작은 변경 없음.

효과 · 실제 비교 — N+1 쿼리

팀 수만큼 DB를 치던 코드

이유 설명 없이 바꾸지 않는다. 무엇이 문제였는지, 왜 더 빠른지 함께 나온다.

Before — N번 쿼리 (팀 수만큼)
for (const team of teams) {
  users.push(await db.query(
    'SELECT * FROM users WHERE team_id = ?',
    team.id
  ));
}
After — 1번 쿼리
const users = await db.query(
  'SELECT * FROM users WHERE team_id IN (?)',
  teams.map(t => t.id)
);
// getUsersByTeam: N+1 → JOIN. n번 왕복 → 1번.

사용법 · 이렇게 켠다

말 한 마디면 된다

최적화가 필요한 코드를 붙여넣고 트리거 표현을 말하면 즉시 시작된다.

영어 트리거 "optimize" / "make it faster" / "ponytail" / /ponytail
한국어 트리거 "최적화" / "빠르게" / "성능 개선" / "코드 최적화"
특정 블록 건너뛰기 "skip this one" — 의도적으로 읽기 쉽게 둔 코드는 제외할 수 있다.
끄는 방법 "done" / "stop ponytail" / "완료"

사용법 · Ponytail이 빛나는 상황

이럴 때 켜세요

✓ 느린 API 응답 DB 왕복이 많거나 루프 안에 쿼리가 있다는 걸 알 때. 가장 큰 병목부터 잡아준다.
✓ 코드 리뷰 전 PR 올리기 전 성능 이슈를 먼저 잡고 싶을 때. 동작 변경 없이 안전하게.
✓ 프로파일러 결과 후 병목 위치를 찾았고 어떻게 고쳐야 할지 모를 때. 이유 있는 수정을 제안한다.
✓ 레거시 코드 개선 오래된 코드에서 큰 임팩트부터 걷어내고 싶을 때. 범위를 벗어나지 않는다.

사용법 · 현재 작업에만 적용된다

대화 전체를 최적화 모드로 만들지 않는다

Caveman과 달리 Ponytail은 현재 작업 단위로만 적용된다. 최적화가 필요한 코드를 논의할 때만 켜고, 끝나면 자동으로 범위를 벗어난다.

이런 제어가 가능하다

특정 파일만 최적화 — 다른 코드에는 적용 안 함 "skip this one" — 의도적으로 남긴 코드는 건너뜀 작업 완료 후 "done" — 깔끔하게 종료 중간에 다시 켜기 — 다음 파일로 넘어갈 때 다시 트리거

안전망 · 데이터 없이 최적화하지 않는다

실제로 느린지 모르면 손대지 않는다

프로파일링 데이터 없이 "여기가 느릴 것 같다"는 이유로 최적화하는 것은 가장 흔한 실수다. Ponytail은 이걸 자동으로 막는다.

조기 최적화 예시:

> Skip: No profiling data confirms this loop
> is a bottleneck.
> Current avg. response time: < 2ms.
>
> Optimizing here risks readability loss
> with no measurable gain.
> Run a profiler first, then re-invoke /ponytail.

Ponytail resume. Next target: getUsersByTeam N+1.

안전망 · 이 상황에서는 최적화를 건너뛴다

안 하는 것도 최적화다

✗ 프로파일링 데이터 없음 실제로 느린지 확인되지 않은 코드는 건너뛰고 이유를 알려준다.
✗ 동작이 바뀌는 수정 빠르게 만들 수 있어도 결과가 달라진다면 적용하지 않는다.
✗ 라이브러리 업그레이드 필요 직접 적용하지 않고 "이 라이브러리로 바꾸면 빠르다"고 알려만 준다.
✗ 의도적으로 읽기 쉬운 코드 테스트·데모·예제 코드는 건드리지 않는다. 목적이 다르다.

정리 · 지금 바로 써보세요

느린 코드에 "ponytail"이라고 말해보세요

Ponytail은 "빠르게 해줘"와 다르다. 임팩트 순서가 정해져 있고, 이유가 설명되고, 동작은 절대 바뀌지 않는 구조적인 최적화다.

지금 바로 써보기 느린 코드를 붙여넣고 "ponytail" 또는 "최적화"라고 입력하면 즉시 시작된다.
스킬 파일 설치 SKILL.md를 Claude 설정에 추가하면 /ponytail 슬래시 커맨드로도 켤 수 있다.
